# 多方案融合流程项目验收记录

**验收日期**：2026-10-16  
**验收范围**：多方案融合页面从选择来源、提交规则、生成融合结果、反馈修订到导出的真实浏览器交互  
**验收环境**：本地 Docker Compose 工作台，`http://localhost:18080/`  
**依赖服务**：本地 MySQL、Redis、Mock LLM 和 Mock 图片服务  
**验收项目**：松萝茶包装升级

## 一、验收目标

确认客户可以在现有 VI 设计工作台中完成以下闭环：

1. 从已有方案中选择多个来源方案。
2. 填写融合方案名称、品牌策略、视觉语言、生产约束和额外限制。
3. 提交融合规则并等待异步融合任务完成。
4. 在方案列表中查看新的融合结果。
5. 对融合结果提交客户反馈并生成二轮修订。
6. 下载 PDF、设计说明和完整打包文件。

## 四、验收结论

多方案融合页面的核心浏览器交互链路已通过：

```text
选择来源方案
→ 填写融合规则
→ 异步生成融合方案
→ 查看融合结果
→ 提交客户反馈
→ 生成二轮修订
→ 触发 PDF / Markdown / ZIP 导出
```

本次没有发现阻断核心流程的页面错误、任务失败或状态停滞。验收使用的是本地 Mock LLM 和 Mock 图片服务，结果证明页面、API、异步队列和数据持久化能够协同工作。

## 五、仍需补充的验证项

以下项目不影响本次本地 Mock 验收结论，但建议在下一轮验收或上线前补充：

1. **全新项目验收**：从 `draft` 项目开始，先完成 Brief，再进入首轮方案和多方案融合，确认没有依赖历史项目数据。
2. **真实 LLM / 图片服务验收**：使用生产配置验证真实模型输出质量、图片生成成功率、超时和重试行为。
3. **导出文件实体验证**：在浏览器下载目录中检查 PDF、Markdown 和 ZIP 是否真实落盘，并确认 PDF 中包含融合结果图片、中文字体和融合来源说明。
4. **刷新与恢复**：生成任务进行中刷新浏览器或重新打开项目，确认融合状态、输出方案和反馈结果仍然可恢复。
5. **异常交互**：验证少于 2 个来源、超过 5 个来源、来源跨项目、任务失败和队列不可用时的页面提示。
6. **权限隔离**：使用另一个客户账号验证无法读取或生成其他客户项目的融合会话。
7. **视觉质量评审**：由设计师检查融合方案在品牌一致性、构图、文字可读性、包装结构和生产工艺上的可执行性。
8. **响应式页面**：补充窄屏和移动端浏览器下的融合卡片、方案列表和导出按钮检查。
